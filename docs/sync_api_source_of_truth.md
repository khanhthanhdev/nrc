# NRC Web <-> Local App Sync API Source of Truth

## Document Status

- Status: source of truth consolidated from `docs/nrc_sync_api_spec.md` and `docs/local_sync_api_spec.md`
- Date: 2026-04-28
- Audience: NRC Web developers, local app developers, event operators, admin tooling developers
- NRC Web machine namespace: `/api/sync/v1`
- Local app HTTP base path: `/api`
- Current NRC Web local base URL: `http://localhost:3001`
- OpenAPI document: `/openapi.json`
- Current sync schema version: `2026-03-08`
- Current supported season: `2025`
- Current supported season definition version: `2025.1`

## 1. Purpose

NRC Web owns event setup before competition day: season, event, approved registrations, teams, sync policy, and machine credentials.

The local app owns event operations during competition day: inspection schedule, inspection results, match schedule, match results, rankings, and awards.

This document is the single contract between the two systems. It defines:

- NRC Web machine API consumed by the local app
- NRC Web admin API used to provision credentials, policy, and inspect batch history
- local app admin API used by operators and the React UI
- shared payload schemas, status mapping, retry behavior, and limitations

## 2. System Boundary

### 2.1. NRC Web owns

- seasons
- events
- team registrations
- approved team roster
- team operational profiles
- sync clients and bearer secrets
- event sync policy
- automatic publication of local app pushes
- public web views after data is accepted

### 2.2. Local app owns

- local event shell after bootstrap
- event-day operational database
- inspection schedule and results
- match schedule and results
- rankings
- awards
- outbound queue and retry policy
- operator-facing outbound sync status

### 2.3. Canonical event identity

```ts
type EventIdentity = {
  season: string;
  eventCode: string;
  eventKey: `${string}/${string}`; // "<season>/<eventCode>"
};
```

For NRC Web machine routes, event identity is derived from the bearer secret. Machine requests must not include event identity in the path.

## 3. Versioning

Two versions are required:

| Version | Meaning | Current value |
| --- | --- | --- |
| `schemaVersion` | Sync wire contract version | `2026-03-08` |
| `definitionVersion` | Season ruleset and payload detail version | `2025.1` |

Local app rule:

1. Call bootstrap first.
2. Read `resources.eventManifest.definitionVersion`.
3. Fail closed if the local app does not support that definition version.
4. Push using the bootstrap `definitionVersion` and current `schemaVersion`.

## 4. Auth and Secrets

### 4.1. NRC Web machine auth

Machine endpoints use an event-scoped bearer secret:

```http
Authorization: Bearer <machine secret>
Content-Type: application/json
Accept: application/json
```

Machine secrets are:

- generated by NRC Web
- shown exactly once
- hashed at rest
- scoped to one event
- revoked when a replacement client is created for the same event

Production requirements:

- treat the secret like a password
- store in secure local app configuration
- never log it
- never include it in screenshots, crash reports, or support bundles
- use HTTPS in production

### 4.2. NRC Web admin auth

NRC Web admin endpoints require a Better Auth staff session with `ADMIN` role.

### 4.3. Local app admin auth

Local app endpoints use local app sessions:

- global admin session token for base URL config and event bootstrap
- event admin session token for event outbound sync status and retry

## 5. Resource Ownership

### 5.1. Web-owned pull resources

Returned by remote bootstrap:

- `season_definition`
- `event_manifest`
- `approved_registrations`
- `team_operational_profiles`
- `sync_policy`

### 5.2. Local-owned push resources

Published by local app to NRC Web:

| Resource type | Mode | Semantics |
| --- | --- | --- |
| `inspection_schedule` | `replace_snapshot` | Full inspection schedule snapshot |
| `inspection_results` | `upsert` | Incremental inspection result updates |
| `match_schedule` | `replace_snapshot` | Full match schedule snapshot |
| `match_results` | `upsert` | Incremental match result updates |
| `team_rankings` | `replace_snapshot` | Full rankings snapshot |
| `team_awards` | `replace_snapshot` | Full awards snapshot |

For `replace_snapshot`, omission means removal when the batch is applied. Always send the full intended state for that resource type.

## 6. High-Level Flow

### 6.1. Provision and bootstrap

1. NRC Web admin creates a sync client for an event.
2. NRC Web returns a one-time machine secret.
3. Operator opens local app `/sync/event`.
4. Operator enters NRC Web base URL, local event code, and machine secret.
5. Local app calls NRC Web `GET /api/sync/v1/machine/bootstrap`.
6. Local app validates the bootstrap response.
7. Local app creates the local event shell and stores outbound link metadata.

### 6.2. Push

1. Local event data changes.
2. Local app calls `requestEventSync(eventCode)`.
3. Local app debounces changes for `1500ms`.
4. Local app builds and stores an outbound batch with status `queued`.
5. Background worker checks due batches every `1000ms`.
6. Worker sends `POST /api/sync/v1/machine/push` to NRC Web.
7. NRC Web applies, rejects invalid input, or returns duplicate.

## 9. Machine Push

### 9.1. Request

```http
POST /api/sync/v1/machine/push
Authorization: Bearer <machine secret>
Content-Type: application/json
Accept: application/json
```

```ts
type PushSyncBatchRequest = {
  schemaVersion: "2026-03-08";
  definitionVersion: "2025.1";
  batchId: string;
  producedAt: string;
  source?: {
    appVersion: string;
    deviceId?: string;
    databaseId?: string;
  };
  resources: PushResource[];
};
```

Field rules:

| Field | Required | Rule |
| --- | --- | --- |
| `schemaVersion` | yes | Must equal `2026-03-08` |
| `definitionVersion` | yes | Must be supported for event season. Current value: `2025.1` |
| `batchId` | yes | Unique per client and event. UUIDv7, ULID, or sortable unique ID recommended |
| `producedAt` | yes | ISO 8601 UTC batch creation time |
| `source.appVersion` | no | Strongly recommended |
| `source.deviceId` | no | Optional machine identifier |
| `source.databaseId` | no | Optional local DB identifier |
| `resources` | yes | One or more resource payloads |

### 9.2. Resource envelope

```ts
type PushResource = {
  resourceType: MachinePushResourceType;
  schemaRef?: string;
  mode: "upsert" | "replace_snapshot";
  records: unknown[];
};
```

Recommended `schemaRef` format:

```text
season/<season>/<resourceType>@<definitionVersion>
```

Example:

```text
season/2025/match_results@2025.1
```

Rules:

- if `schemaRef` is provided, it must contain `@`
- version suffix after `@` must equal the batch `definitionVersion`

### 9.3. Idempotency

Idempotency key:

- `syncClientId`
- `batchId`
- canonical payload hash

Outcomes:

| Retry payload | Result |
| --- | --- |
| same `batchId`, same canonical payload | success with `status: "duplicate"` |
| same `batchId`, different canonical payload | `409 BATCH_HASH_MISMATCH` |

Canonical hashing behavior:

- object keys are canonicalized
- array order is preserved

Local app requirements:

- generate a fresh `batchId` for each new logical batch
- retry timeout or transport failures with the exact same payload and array order
- persist original batch payload until NRC Web acknowledges it
- never reuse a `batchId` for corrected data

## 11. Push Validation and Response

### 11.1. NRC Web validation

NRC Web validates:

- top-level schema shape
- supported `schemaVersion`
- supported `definitionVersion`
- allowed resource types for event policy
- uniqueness of `resourceType + normalized record key` within the batch
- `schemaRef` version consistency
- alliance-level match rules

Unknown teams currently create validation warnings in the push receipt and batch history.

### 11.2. Response

```ts
type PushSyncBatchResponse = {
  batchId: string;
  status: "validated" | "applied" | "duplicate" | "rejected" | "failed";
  changeSetId?: string;
  receivedAt: string;
  warnings?: Array<{
    code: string;
    message: string;
    resourceType?: MachinePushResourceType;
    recordKey?: string;
  }>;
};
```

Current machine push terminal success statuses:

- `applied`
- `duplicate`

The machine route does not currently return `validated` as terminal success.

### 11.4. Push errors

| HTTP | Code | Meaning | Client action |
| --- | --- | --- | --- |
| 400 | `VALIDATION_FAILED` | Payload shape or business validation failed | Fix data and resend with new `batchId` |
| 400 | `UNSUPPORTED_DEFINITION_VERSION` | Sent unsupported season definition | Refresh bootstrap and update support |
| 401 | `UNAUTHORIZED` | Missing or invalid bearer token | Fix credentials |
| 403 | `CLIENT_REVOKED` | Client revoked | Re-provision secret |
| 403 | `CLIENT_EXPIRED` | Client expired | Re-provision secret |
| 403 | `SYNC_DISABLED` | Event sync disabled | Stop pushing and contact admin |
| 403 | `RESOURCE_TYPE_NOT_ALLOWED` | Resource disallowed by policy | Honor bootstrap policy |
| 409 | `BATCH_HASH_MISMATCH` | Same `batchId` with different payload | Generate new `batchId` |

## 12. Review and Publish Model

### 12.1. Batch lifecycle

```text
validated -> applied
validated -> failed
duplicate -> terminal
applied -> terminal
rejected -> terminal
failed -> terminal
```

### 12.2. Automatic publication

Successful local app pushes are applied immediately. Guardrail warnings are recorded on the batch and surfaced in admin history; they do not require approval.

Current guardrails:

- `UNKNOWN_TEAM_REFERENCE`
- `PUBLISHED_MATCH_MODIFIED`
- `SNAPSHOT_SHRINKAGE`
- `AWARDS_MISSING_AFTER_PUBLICATION`

### 12.3. Local app handling for warnings

When a batch response includes warnings, the batch was still published. The local app should keep the warnings visible for operators and continue normal outbound processing.

| --- | --- |
| `baseUrl` | Optional if already stored. Replaces stored value when provided |
| `eventCode` | Required local event code. Normalized and validated by local app |
| `eventKey` | Required remote machine bearer secret. Name is misleading |

`eventCode` must be 1 to 8 alphanumeric characters.

Success:

```json
{
  "success": true,
  "eventCode": "nrc2026",
  "redirectUrl": "/event/nrc2026/dashboard/defaultaccounts"
}
```

Local app internal behavior:

1. Resolve remote base URL from request or stored config.
2. Call remote `GET /api/sync/v1/machine/bootstrap`.
3. Validate bootstrap response against machine schema.
4. Create local event shell.
5. Seed local teams from approved registrations and team operational profiles.
6. Store outbound link metadata:
   - remote base URL
   - remote bearer secret
   - remote event key
   - allowed pull resources
   - allowed push resources
   - sync apply mode
   - schedule owner
   - definition version

Failure cases surfaced by local app:

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | `VALIDATION_FAILED` | Missing or invalid `baseUrl`, `eventCode`, or `eventKey` |
| 401 | `UNAUTHORIZED` | Remote bearer secret rejected by NRC Web |
| 404 | `NOT_FOUND` | Remote bootstrap endpoint missing |
| 500 | `NETWORK_ERROR` | Remote host unreachable |
| 500 | `PARSE_ERROR` | Remote returned non-JSON |
| 500 | `SCHEMA_MISMATCH` | Remote returned incompatible bootstrap data |
| 500 | `REMOTE_ERROR` | Other remote bootstrap failure |

## 15. Local App Outbound Queue

### 15.1. Trigger behavior

The local app does not expose a generic `POST /api/sync/push` endpoint.

Push is driven by `OutboundSyncPushService`:

- event writes call `requestEventSync(eventCode)`
- requests are debounced for `1500ms`
- batch is stored locally with status `queued`
- worker checks due batches every `1000ms`
- due batch is sent to remote `POST /api/sync/v1/machine/push`

### 15.2. Payload generation

Allowed resources are the intersection of:

- outbound link allowed resources
- current sync policy allowed resources

Payload rules:

- built from local event state at enqueue time
- `replace_snapshot` resources contain full intended state
- `upsert` resources contain only records the local app wants to submit

### 15.3. Local batch statuses

| Local status | Meaning |
| --- | --- |
| `queued` | Waiting to be processed |
| `in_flight` | HTTP request in progress |
| `succeeded` | Remote returned `applied` or `duplicate` |
| `failed` | Retryable failure; batch retries after backoff |
| `blocked` | Non-retryable failure; manual intervention required |

### 15.4. Retry behavior

Retryable:

- network errors
- HTTP `408`
- HTTP `425`
- HTTP `429`
- HTTP `500`
- HTTP `502`
- HTTP `503`
- HTTP `504`
- HTTP `409` unless remote error code is `BATCH_HASH_MISMATCH`

Backoff:

- exponential growth
- capped at `300000ms`
- includes jitter

Remote-to-local mapping:

| Remote result | Local result |
| --- | --- |
| `200` with `status: "applied"` | `succeeded` |
| `200` with `status: "duplicate"` | `succeeded` |
| retryable HTTP failure | `failed` |
| non-retryable HTTP failure | `blocked` |
| local config/link missing | `blocked` |

## 17. Deterministic Serialization

Before submitting a batch:

1. sort snapshot records deterministically
2. preserve stable array ordering between retries
3. normalize optional fields consistently

Suggested ordering:

- inspections by `teamNumber`, then `stage`
- matches by `phase`, then `matchNumber`, then `playNumber`
- rankings by `rank`, then `teamNumber`
- awards by `displayOrder`, then `awardCode`

## 18. Bootstrap Refresh Triggers

Local app should refresh bootstrap:

- at local app startup
- after sync secret rotation
- after operator reconfiguration
- after `UNSUPPORTED_DEFINITION_VERSION`
- after repeated `RESOURCE_TYPE_NOT_ALLOWED`

## 19. Operator Sequence

1. NRC Web admin creates sync client for event.
2. Admin copies one-time machine secret.
3. Operator opens `/sync/event` in local app.
4. Operator confirms or enters NRC Web base URL.
5. Operator pastes machine secret into `eventKey` field.
6. Operator enters local event code.
7. Operator submits bootstrap.
8. Operator verifies outbound status:
   - `hasOutboundLink: true`
   - `isSyncEnabled: true`
9. If pushes stall, inspect `lastError` and use outbound retry.

## 21. Current Limitations

1. Machine clients only have `GET /machine/bootstrap` and `POST /machine/push`.
2. There is no incremental pull API.
3. There is no machine-side batch-status polling endpoint.
4. Only season `2025` with `definitionVersion: "2025.1"` is implemented.
5. `team_awards` is effectively unique by `awardCode` per event in the published projection.
6. Admin batch listing exposes `cursor`, but pagination currently only supports `limit`; `nextCursor` is not emitted.
7. `scheduleOwner` is policy metadata; machine push acceptance is governed by `isSyncEnabled` and `allowedPushResources`.
8. In bootstrap, `syncPolicy.updatedAt` currently reflects bootstrap generation time, not persisted policy update timestamp.
9. Local bootstrap request field `eventKey` is actually the remote machine bearer secret.
